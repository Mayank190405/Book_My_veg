## Executive finding

**Neither reported balance can be accepted as the verified receivable from source alone. The application has two materially different definitions of outstanding balance, including two definitions inside the Audit Ledger screen itself.**

- Customer/driver/public-pay dues sum collectible balances of individual orders. Orders flagged `isPaid=true` or payment status `COMPLETED`, `PAID`, or `SETTLED` contribute zero due, even without supporting payment rows.
- Audit Ledger headline outstanding is `max(0, selected order charges − valid customer Payment rows)`. It does not create a balancing credit for those paid flags.
- The Audit Ledger's bill-wise tab uses the first definition. Its headline uses the second. Consequently, 11 purchases and one due bill are entirely possible in the same response.
- A confirmed delivery path marks orders fully paid even when no pending COD payment exists. A confirmed partial-COD completion path deletes the pending COD remainder after receiving an advance. These can combine to leave a paid flag without matching collections.
- The report also has a confirmed scope defect: purchase filters are not applied to its second payment query. Cancelled/failed orders' payments and other out-of-scope payments can reduce the statement balance.

Some may be underpaid and others overpaid; the figures do not identify individual orders. Whether the gap represents missing history, incorrect flags, removed payments, or genuinely unpaid purchases requires database and receipt evidence.

With 11 charge events, 19 ledger entries imply eight recognized payment events in this implementation, assuming the numbers came from one unchanged response. This does not mean eight independent gateway transactions: one receipt can be allocated across multiple orders, and one order can have multiple receipts.

## 1. Payment architecture map

```text
WEB checkout / integration order creation
  → orderController / integration/orderController
  → orderService.placeOrder → serializable transaction/retry
  → Order + OrderItem + PENDING Payment + inventory + status history

Legacy payment initiation
  → paymentController.initiatePayment → separate order/payment creation path

POS checkout / credit / split tender
  → posController.processPOSOrder
  → Order + SUCCESS Payment slices + optional wallet debit + drawer counts
  → separate post-transaction allocation to old dues

Easebuzz / Juspay initiation and completion
  → paymentController link/session creation
  → callback / webhook / verifyPayment / Easebuzz sync
  → completeOrderPayment
      → single order posting, or settleDuesForCustomer
      → Payment + order flags/counters + status history + notifications

Cash collection / manual paid flag
  → orderController cash/OTP/manual-payment handlers
  → separate SUCCESS-only allocation logic

Wallet deposit
  → POS deposit or online processWalletDepositCredit
  → User.accountBalance + WalletTransaction
  → order Payment only when wallet is spent

Display
  → dueCalculationService.calculateOrderDue / calculateCustomerDues
      → POS history, driver/customer dues, public pay/invoice, reminders, cache
  → dashboardController.getCustomerDetailedReport
      → synthetic charges and Payment events → chronological headline ledger
      → calculateOrderDue → separate bill-wise tab
  → sales/customer reports and shift cash → additional independent reducers

Maintenance
  → duplicate cleanup; financial audit/reconciliation; Easebuzz cron
  → mutate the underlying rows from which the synthetic ledger is rebuilt
```

The displayed Audit Ledger is **not an immutable customer journal**. Its charge/payment events are reconstructed from current `Order` and `Payment` rows on every request. Changing flags, totals, payment status, allocations, or deleting rows can change historical results. `AuditLog` is evidence/supporting metadata; it is not the statement's financial source.

## 3. Transaction lifecycle analysis

### Web online and COD orders

`POST /orders` validates shape and nonnegative submitted total, then `orderService.placeOrder` reserves stock, computes coupon discount, creates Order/items/status history and pending payments inside `withTransactionRetry` using Serializable isolation. It clears cart and schedules auto-cancel. Actual total is submitted `totalAmount − discount`, not a fully authoritative recomputation of item prices, taxes and delivery charges. A submitted nonzero item price is retained. See [orderService.ts:75](/Users/kradsagency/Book_My_veg/server/src/services/orderService.ts:75), [orderService.ts:130](/Users/kradsagency/Book_My_veg/server/src/services/orderService.ts:130), [schema validation](/Users/kradsagency/Book_My_veg/server/src/schemas/orderSchemas.ts:1).

ONLINE creates a full pending ONLINE record and `PAYMENT_PENDING` order. COD eligibility is based on delivered-order history since a cancelled/failed/returned reset: first order online; next order advance max(₹40,10%); next max(₹20,5%); subsequent full COD. Partial COD creates both pending ONLINE advance and pending COD remainder. Full COD creates pending COD and CONFIRMED order.

Pending payments do not reduce bill dues or ledger. Successful gateway completion updates/creates a SUCCESS payment, sums SUCCESS rows, marks PARTIAL/COMPLETED and confirms early-stage orders. It writes notification/history and increments `easebuzzCollected` even for completion methods that are not necessarily Easebuzz. **It deletes all remaining PENDING payment rows even on partial completion**, including the COD remainder. See [paymentController.ts:1037](/Users/kradsagency/Book_My_veg/server/src/controllers/paymentController.ts:1037).

`updateOrderStatus(...DELIVERED)` converts one pending COD row to SUCCESS and marks the order fully paid. If no pending COD row exists, it still sets `isPaid=true/paymentStatus=COMPLETED` without a receipt. Delivery status is written before the financial block, so those changes are not one atomic operation. [orderController.ts:274](/Users/kradsagency/Book_My_veg/server/src/controllers/orderController.ts:274).

Legacy `POST /payments/initiate` independently creates an order and full pending payment with submitted amount, deducts stock immediately, then initiates the gateway. It is a second order creation path, with no equivalent populated order idempotency key. [paymentController.ts:176](/Users/kradsagency/Book_My_veg/server/src/controllers/paymentController.ts:176).

### POS cash, credit, split payment and edits

`processPOSOrder` reads an existing order/payment total if editing and customer previous dues before its transaction. Total is JS `sum(price × quantity) − discount`. It creates/edits order/items, deducts stock, records every positive split slice as SUCCESS, sets payment flags, optionally deducts wallet balance, and updates cash denominations. Credit normally creates no money receipt, leaving dues outstanding. `suspend` suppresses stock/payment posting but leaves an active PENDING order, which current dues queries do not exclude merely for being suspended. [posController.ts:445](/Users/kradsagency/Book_My_veg/server/src/controllers/posController.ts:445).

Online/UPI-style slices recorded directly by this POS handler are staff assertions; there is no gateway verification in this posting loop. A retry/edit with the same payment slice can append a new receipt. Editing reads prior totals outside the transaction and does not provide durable request idempotency. Wallet checkout clamps balance to zero instead of rejecting insufficient funds, yet posts the full payment amount.

Old dues entered at checkout are allocated oldest-first **after** the new-bill transaction, using separate payment creates and order updates. Failure can commit the new bill and only some historical settlements. This block does not debit wallet for a WALLET old-dues amount. Customer cache sync is best effort. Invoice WhatsApp dispatch happens after commit. [posController.ts:725](/Users/kradsagency/Book_My_veg/server/src/controllers/posController.ts:725).

### Bill-specific partial or full collection

`collectDuePayment` loads the order and computes due before opening its transaction. It parses positive slices, computes `toApplyTarget=min(sum(slices), remainingDue)` and overflow, then writes a Payment **with amount toApplyTarget inside every slice iteration**. Example: ₹100 due paid as ₹40 CASH + ₹60 EASEBUZZ writes two ₹100 payments; order flags/response are based on ₹100 while rows total ₹200. This is a confirmed defect, independent of concurrency. [posController.ts:1267](/Users/kradsagency/Book_My_veg/server/src/controllers/posController.ts:1267), [posController.ts:1294](/Users/kradsagency/Book_My_veg/server/src/controllers/posController.ts:1294).

Overflow allocates oldest-first to other eligible orders but labels them with the first slice's method, losing tender attribution. Excess beyond all eligible bills is not credited to wallet or recorded as unapplied money. There is no replay check on supplied transaction ID. The online POS callback also explicitly calls collect-due, so a gateway webhook and frontend completion are competing posting paths; a completed-order guard can stop some repeats but partial/split callbacks remain unsafe. [POS frontend:699](/Users/kradsagency/Book_My_veg/client/src/app/pos/page.tsx:699).

Wallet collection attempts a WalletTransaction using `orderId` (not in this model) without mandatory `balanceAfter`, catches the error, and has no `User.accountBalance` decrement. Against the checked-in schema it cannot produce the intended valid wallet debit. Whether the whole transaction fails or proceeds depends on where validation fails; a caught database error can also leave a PostgreSQL transaction aborted. It must not be treated as a working wallet deduction. [posController.ts:1275](/Users/kradsagency/Book_My_veg/server/src/controllers/posController.ts:1275), [wallet schema](/Users/kradsagency/Book_My_veg/server/prisma/schema.prisma:1071).

### Account settlement and gateway multi-bill settlement

`SETTLE ACCOUNT` calls `/pos/customers/:id/settle`. It queries only eligible unpaid orders, orders oldest-first, uses Decimal allocation, creates SUCCESS receipts and updates order flags inside a transaction, adjusts cash denominations, then synchronizes cached dues. It does not settle the synthetic headline gap on orders already flagged paid. It returns only allocated value; excess is not persisted as credit. It accepts method without a corresponding wallet debit or gateway verification and has no durable replay guard. [posController.ts:1443](/Users/kradsagency/Book_My_veg/server/src/controllers/posController.ts:1443).

The shared allocator caps at each bill's raw `total − valid payments`; for its positive-money path it does not itself check paid flags or cancelled status. Its callers must supply eligible orders. [dueCalculationService.ts:450](/Users/kradsagency/Book_My_veg/server/src/services/dueCalculationService.ts:450).

`initiatePayDue` resolves customer/bill, determines intended allocations, creates a PAYMENT_REQUEST audit record with expectedAmount/billIds and PENDING Payment rows, then initiates the gateway. These preparation writes are not one atomic operation and errors are tolerated. Short transaction IDs encode customer/bill/phone and timestamp suffix. [paymentController.ts:1870](/Users/kradsagency/Book_My_veg/server/src/controllers/paymentController.ts:1870).

`settleDuesForCustomer` checks for an existing SUCCESS transaction or suffixed allocation, resolves saved request/customer, takes selected bills, preferred bill, then remaining customer unpaid orders. It allocates via Decimal and writes SUCCESS receipts with suffixed IDs, flags/counters/history/notifications in one default-isolation transaction. It logs excess to PAYMENT_EXCESS, but does not store that excess as spendable wallet credit. It updates the request log to SETTLED and syncs customer cache. ExpectedAmount and originally intended per-bill amounts are stored but are not enforced as a verified payment contract. Explicit bill selection is not constrained to the resolved customer's ownership. Fallbacks include phone/email/user-prefix matching. [paymentController.ts:462](/Users/kradsagency/Book_My_veg/server/src/controllers/paymentController.ts:462).

### Driver cash and manual paid/unpaid controls

Cash OTP verification validates an OTP keyed to order/customer; direct collection does not require OTP. Both use a separate SUCCESS-only payment sum and JS number arithmetic. Multi-bill collection selects PENDING/PARTIAL noncancelled orders and caps oldest-first allocations. Single-bill collection posts the submitted amount without capping to due or excluding already-paid/cancelled orders in that branch. Both update `cashCollected`, flags/history and customer cache in a transaction, with no payment-event idempotency key. Unallocated multi-bill excess is not recorded. [orderController.ts:1006](/Users/kradsagency/Book_My_veg/server/src/controllers/orderController.ts:1006), [orderController.ts:1153](/Users/kradsagency/Book_My_veg/server/src/controllers/orderController.ts:1153).

Manual paid=true promotes the first pending payment, regardless of whether it covers the full remainder; otherwise creates a full-order-total receipt even when partial successful payments already exist. Flags are set fully paid either way. Paid=false changes all SUCCESS receipts to PENDING rather than posting a reversal. Audit is written after the transaction. Repeated paid=true can add another full receipt where no pending row exists. [orderController.ts:417](/Users/kradsagency/Book_My_veg/server/src/controllers/orderController.ts:417).

### Wallet credit and debit

POS deposit adds to `User.accountBalance` and writes DEPOSIT with balanceAfter inside a transaction; no replay check. Online deposit creation starts an Easebuzz/mock flow. Callback/webhook/verify call `processWalletDepositCredit`, which performs a find-before-create reference check, reads current balance, writes absolute new balance and a DEPOSIT row. No unique reference or row lock makes that check atomic against concurrency. Simultaneous deposits can duplicate or overwrite balance increments. Receipt dispatch occurs inside the credit transaction, creating an external side effect that cannot roll back with the database. [paymentController.ts:2560](/Users/kradsagency/Book_My_veg/server/src/controllers/paymentController.ts:2560), [posController.ts:1729](/Users/kradsagency/Book_My_veg/server/src/controllers/posController.ts:1729).

POS normal checkout creates PAYMENT_DEDUCTION and subtracts from accountBalance, but permits insufficient funds through clamping. Bill collection and account settlement have the inconsistencies described above. POS history reconstructs wallet balance from only the **latest 20** transactions and treats every non-DEPOSIT type as a subtraction, so REFUND/positive ADJUSTMENT cannot be assumed correct and older opening balance is lost. Wallet details instead returns stored accountBalance. [posController.ts:899](/Users/kradsagency/Book_My_veg/server/src/controllers/posController.ts:899), [paymentController.ts:2749](/Users/kradsagency/Book_My_veg/server/src/controllers/paymentController.ts:2749).

### Refunds, cancellations and abandoned payments

`refundPayment` always invokes Juspay, even though Easebuzz is another payment provider. It skips only if current paymentStatus is REFUNDED; requests use a new timestamp-based refund ID, with no lock across concurrent calls. A successful refund, including a requested partial refund, marks the entire order CANCELLED/REFUNDED and creates a **positive SUCCESS JUSPAY_REFUND Payment**. The standard validator accepts it as incoming money, while cancelled order charges are excluded from the detailed statement. Consequently the report can deduct both original receipt and refund as collections without the cancelled charge. [paymentController.ts:1651](/Users/kradsagency/Book_My_veg/server/src/controllers/paymentController.ts:1651).

Regular web/POS cancellation restores inventory and changes order status, but does not automatically reverse/refund cash, gateway receipts or wallet deductions. POS `refundMode` is read but unused. These are cancellation operations, not complete financial reversal workflows. [orderService.ts:289](/Users/kradsagency/Book_My_veg/server/src/services/orderService.ts:289), [posController.ts:1131](/Users/kradsagency/Book_My_veg/server/src/controllers/posController.ts:1131).

Failure verification can restore inventory and physically delete order items, payments, history and order. Auto-cancel does the same after reading status outside the transaction. A delayed gateway success may subsequently be unmapped because its order no longer exists; concurrent success versus purge is a race. Non-success client-supplied verification can purge a partially paid order if its flags are not fully completed. ## 4. Exact dues calculation comparison

### Shared bill calculator

`isValidPaymentRecord`: amount > 0, trimmed case-insensitive method != CREDIT, and status blank/null or trimmed case-insensitive SUCCESS/COMPLETED/PAID. PENDING/FAILED/REFUNDED/USER_DROPPED/CANCELLED and other statuses do not count. CHARGED is not a valid stored Payment status under this validator; gateway completion converts it to SUCCESS. Schema requires status, but code intentionally tolerates legacy absent values.

For bill total T and recognized receipt sum P:

```text
Cancelled or failed → due 0, reported paid 0
isPaid true OR paymentStatus COMPLETED/PAID/SETTLED
    → due 0, reported paid T (not actual receipt sum)
Otherwise → reported paid P, due max(0,T−P)
Residual <= ₹0.005 → ineligible/zero due
Customer due → sum positive eligible per-bill dues
```

This uses Decimal before two-decimal conversion. It nets overpayments only within a bill: one bill's credit does not automatically offset another bill's debt.

## 6. REMOVE DUPLICATES analysis

The Audit Ledger button posts `/payments/cleanup-duplicates` without customer or location parameters. It invokes a **global** routine, although direct Order reads can additionally be narrowed by request context. Its Payment grouping/deletions are not scoped to the visible customer. Roles permitted include POS_OPERATOR and MANAGER in the payment router.

The routine:

1. Groups SUCCESS by orderId and nonnull transactionId; keeps oldest and audits/deletes later rows. It does not compare amounts or verify the gateway. Cross-order allocations sharing a transaction ID are preserved by grouping on both fields.
2. Examines multi-SUCCESS orders with raw paid > total. It treats same-method, near-equal amount (<₹0.01), within-five-minute receipts as duplicates when removing one would still cover the order total within tolerance. Different real gateway IDs do not prevent deletion. Equal genuine receipts/overpayments can therefore be removed.
3. Recomputes paid flags for examined overpaid orders, deletes pending rows for fully paid orders, syncs cache, then purges pending records for other flagged-paid orders.

The first pass syncs dues without necessarily recomputing that order's paid flags; if deletion leaves only one receipt, the second pass may not visit it. A flagged-paid order can remain unsupported by receipts. There is no encompassing transaction; audit/delete/status/cache can become partially applied. Errors are caught/logged internally, so the outer controller can still return success. [paymentController.ts:2375](/Users/kradsagency/Book_My_veg/server/src/controllers/paymentController.ts:2375).

Deleting successful receipts increases the raw ledger balance while paid flags may keep dues at zero. This is a plausible mechanism for a positive ledger-versus-dues difference, but there is no evidence yet that this customer had such deletion.

The separate script `cleanDuplicatePayments.ts` is less discriminating: after accumulated SUCCESS amounts cover an order, it deletes subsequent receipts regardless of transaction ID/method/time, then updates flags. It lacks the controller routine's purge audit trail. Do not confuse the two implementations.

## 9. Discrepancy analysis and required verification

### What source establishes

1. Order counts differ because “one due bill” counts eligible unpaid residuals, whereas “11 orders” counts historical noncancelled/nonfailed purchases, including flagged-paid orders. Order-count difference alone is not a defect.
2. Paid flags override receipt sums for dues; they do not produce payment events in the headline ledger.
3. A Payment row is not counted twice merely because both detailed-report queries select it: processedPaymentIds deduplicates IDs. Separate duplicate rows are counted independently.
4. The two amounts appear intended as customer outstanding, but are not computed as the same financial quantity. They agree only with consistent scopes, complete valid allocations, flags matching money, and correct handling of credits/refunds.
5. `SETTLE ACCOUNT` cannot repair missing historical receipts on already-settled orders because its eligibility query excludes those orders.

For the same active order population, let T_i be total, P_i be valid payments, F_i mean flagged settled, and P_out be valid receipts on excluded orders. Ignoring only sub-paise threshold rounding:

```text
Ledger = max(0, Σ T_i − Σ P_i − P_out)
Bill dues = Σ over not-F_i max(0,T_i−P_i)
```

When the ledger is positive, their difference can arise from flagged-settled residuals, minus overpayments on unflagged orders, minus out-of-scope payments. Different populations add another scope term. Thus ₹1,629.55 is not automatically a single missing receipt or a single unpaid bill.

### Ranked verification hypotheses

1. **Historical paid flags without enough valid payment rows:** most direct match to ledger > bill dues. Check the ten other orders for net charge/payment shortfalls, then delivery/manual-mark status history.
2. **Payment deletion or status changes with surviving paid flags:** look for cleanup/reconciliation purge audits and manual reversals; first cleanup pass can leave this state. Do not infer deletion only because there are fewer payments than orders.
3. **Different customer/channel/location/date scopes:** collect both actual request URLs, customer UUID, caller role/location and request times. Frontend statement loses parent date/location, and Prisma adds context filtering.
4. **Gateway money received but unmapped/not posted:** compare saved PAYMENT_REQUEST expectedAmount and allocations, unmapped audit entries, provider events and bank settlements. Order purge, truncated identifiers and response mismatch can explain missing rows.
5. **Unsupported statuses/methods and refunds:** inspect all payment records, not only SUCCESS; account for positive refund records, CREDIT notes, cancelled orders and excluded-scope receipts. These can offset the net discrepancy.
6. **Split duplication/overpayment/reallocation and cleanup interactions:** can inflate payment totals and later remove them. They are confirmed defective mechanisms but their participation in this case is unproven.

### Specific records and queries to approve separately

The proposed [read-only SQL](/private/tmp/book-my-veg-payment-verification.sql) is **not executed**. It includes:

- Exact User identity, stored totalDue/accountBalance.
- Every customer Order, including cancelled/failed, with flags, channel/location, amounts and collection counters.
- Per-order valid payment sum versus SUCCESS-only sum and flag-based due; this isolates unsupported paid flags.
- One-snapshot reconstruction of scoped ledger, bill-wise count/dues, flagged-order net gap and out-of-scope payments.
- Every Payment with ID/amount/status/method/transactionId/time/metadata and candidate duplicate groupings.
- OrderStatusHistory for delivery/manual marking/reversal evidence.
- AuditLog for payment requests, purges, excess, unmapped transactions, and cache corrections.
- Full wallet history and actual database indexes/triggers/legacy tables.

Required parameters: exact customer UUID; actual effective location, channel and raw start/end timestamp filters, null when absent. Capture caller token claims safely without sharing tokens. Use an approved read-only account and a consistent snapshot; the script begins REPEATABLE READ READ ONLY and ends ROLLBACK. SQL reproduces standard two-decimal stored values; unusual whitespace/status encoding and any deployed custom triggers/extensions must also be considered.

Then obtain provider/bank/cash evidence for the eight recognized payment events and any omitted attempts: merchant txnid, provider ID, amount, currency, captured/settled/refunded state, receipt time, allocation target and refund IDs. A SUCCESS database row alone is insufficient evidence given the verification defects. Logs should be searched by identified transaction/order IDs only; they may contain personal data and secrets. This review did not inspect secrets or live logs.

The precise root cause is confirmed only when the identified per-order differences and any scope/refund/credit effects reconcile exactly to ₹1,629.55 and receipts establish which side should change.
